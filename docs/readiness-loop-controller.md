# Readiness-loop wake controller

`scripts/rillcache_pi_wake.py` is the versioned implementation behind the existing ten-minute host timer. The timer remains a lightweight poller; it does not start another Pi process or session. The controller verifies the pinned process identity, completed idle transcript turn, and empty tmux composer before sending anything.

The persistent prompt is versioned at [`scripts/production-readiness-loop-prompt.md`](../scripts/production-readiness-loop-prompt.md). Every final turn must declare either `<!-- RILLCACHE_WAKE: WAITING -->` (no safe work remains until external state changes) or `<!-- RILLCACHE_WAKE: CONTINUE -->` (owned work remains active or a wait is not safely verified). Missing markers fail toward continuing, not suppression.

For a declared wait, the controller fingerprints protected `main`, open PR heads/review/check summaries, and open issue update/assignee/label state using the authenticated `gh` CLI. It suppresses redundant Pi prompts while that fingerprint and prompt version are unchanged. External changes are coalesced for at least one hour after a wake, so a burst of CI check updates produces at most one audit in that window; the newest state is then checked. A 24-hour heartbeat provides a periodic recheck for evidence outside GitHub metadata. If GitHub state cannot be read, the controller fails closed and tries again on the next timer tick. `PAUSE-PI-WAKE` remains an explicit operator pause switch.

The last successful wake fingerprint, prompt hash, and timestamp are stored atomically in `/root/.local/state/rillcache-frame-lifecycle/wake-state.json`. Host-specific `RILLCACHE_PI_*` settings select the session, Pi PID/start ticks, chat transcript and task file; `RILLCACHE_TMUX_PANE_PID` and `RILLCACHE_TMUX_PANE_COMMAND` bind the exact pane process and command when Pi is its child, and the controller verifies the Pi PID is actually a child of that pane. `RILLCACHE_TMUX_SOCKET` selects its tmux socket. The same versioned controller can therefore serve already-existing sessions on multiple cluster machines without assuming the local pane identity. This file is operational state, not acceptance evidence; the readiness checkpoint and append-only ledger remain authoritative. Updating the prompt changes its hash and triggers a fresh cycle. The controller and prompt are standard-library-only Python/Markdown; run `python3 scripts/test_rillcache_pi_wake.py` to exercise wake suppression, external/prompt changes, heartbeat, marker behavior, and state persistence. The packaged units are in [`ops/systemd`](../ops/systemd). Install the script as `/root/.local/bin/rillcache-pi-wake`, the prompt as the local task file, and both units under `/etc/systemd/system`; only enable a timer after verifying the intended idle Pi pane, its transcript, and process identity. For a non-default pane, create root-only `/etc/rillcache/readiness-loop.env` with the corresponding `RILLCACHE_PI_*`, `RILLCACHE_TMUX_PANE_PID`, and `RILLCACHE_TMUX_SOCKET` values.

A timer firing or a wake is not readiness progress. When no safe implementation exists, the loop records a blocker once and waits instead of repeating audits every ten minutes. Production status remains **NOT PRODUCTION READY** until the independent acceptance evidence is complete.
