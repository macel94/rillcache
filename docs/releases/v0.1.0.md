# Rillcache v0.1.0 release notes

Release candidate notes for `v0.1.0`. These notes are the input to
`scripts/cut-release.sh`; the tag is created only by the release owner after every
gate passes.

## Candidate

- Version: `0.1.0` (`Cargo.toml`).
- Candidate commit: the `main` head that contains this file; the exact SHA is
  filled in by the release owner at tag time.
- Container images: `ghcr.io/macel94/rillcache` platform digests recorded by the
  container workflow for that SHA. No digest is claimed here before publication.

## Compatibility profile

The supported surface is the profile in `docs/compatibility.md` at this commit:
RESP2 and the documented RESP3 subset, the command inventory in
`docs/compatibility.md`, DB 0 only, standalone topology. Unsupported capabilities
are listed in `docs/unsupported.md` instead of being implied by silence.

## Changes

See `CHANGELOG.md` under `0.1.0`.

S9 (bounded overload and slow-client behavior) is closed at this candidate by
enforced write-stall shedding and opt-in global/per-user command budgets; the
operator contract is `docs/overload-policy.md` and the evidence is
`tests/overload_policy.rs`, `tests/tls_write_stall.rs`, the admission unit tests
and the pool stall-clock tests. It is no longer listed as an accepted
limitation.

## Migration

None required from a previous tagged release: `0.1.0` is the first versioned
artifact. From an untagged `main` pre-release, replay the existing journal; if the
journal was written by an older format, dump and restore instead.

## Rollback

Rolling back to an untagged `main` build of the same journal format is supported.
Rolling back across a journal format change is unsupported and is called out per
release.

## Support window

Published policy (`docs/release-lifecycle.md`): stable MINOR releases are
supported for 12 months from the release date with PATCH fixes for security and
data-integrity defects; the previous MINOR is supported for 90 days after the next
MINOR ships; older releases are unsupported. Pre-releases carry no support
promise. This window starts on the date the release owner publishes the tag, not
before.

## Accepted limitations

Every open P0 readiness gap at this candidate is accepted here by its checklist
identifier. None of them is claimed as production-ready, and this list is
machine-checked against the canonical checklist so it cannot drift:

- `S1` — open (independent security review); artifacts in `docs/security/`.
- `S5` — open (certificate-status and human security review); native staple
  status/freshness enforcement landed, review outstanding.
- `V1` — open (pinned upstream Tcl coverage of the supported profile).
- `V2` — open (differential corpus completeness).
- `V3` — open (independent acceptance sign-offs); registry in
  `docs/acceptance/signoffs.tsv`.

P1/P2 gaps remain open as well and are not restated individually; the
authoritative list is `docs/production-readiness-gaps.md` and that file wins
over these notes.

## Verification

The declared resident-memory bound (`--memory-bound-bytes` with
`--memory-bound-headroom-bytes`), its derived payload enforcement, `INFO memory`
reporting and the bounded-process allocation-failure drills land with this
candidate and close the memory-accounting criterion in
`docs/production-readiness-gaps.md`.

Tested upgrade, rollback and migration evidence for this candidate:

- Same-binary offline rollback and upgrade/downgrade are exercised by
  `scripts/upgrade_drill.py` against the pinned old/new pair in
  `ci/upgrade-pins.json`; the drill records the accepted data-loss bound and
  fails on an unexpected key, TTL or accounting difference.
- Isolated backup/restore is exercised by `scripts/restore_drill.py` with its
  own regression suite `scripts/test_restore_drill.py`, including active-writer
  refusal, archive and inner-journal corruption, and no-overwrite publication.
- The required CI graph runs both drills as
  `Upgrade and rollback drill` and `Isolated backup/restore drill`, so a
  changed candidate cannot ship notes that describe an unexercised path.
- `python3 scripts/check_release_notes.py` fails when these notes drift from the
  canonical checklist, stop naming an exercised drill, reference a missing path,
  or claim a journal/format change without a migration and rollback position.

Retained failures: the drills cover the journal formats pinned in
`ci/upgrade-pins.json` only. A journal format change outside that pin set has no
tested rollback path and must be treated as unsupported until a drill pair
exists.
