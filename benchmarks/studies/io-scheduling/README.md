Each study has 360 independently revalidated native records: five workloads,
per-client/one/four-worker modes, inherited/one-logical-CPU budgets, pipelines
1/16, three alternating-order repetitions. Every one of the 72 JSON file hashes
was checked and each 60-row summary regenerated byte-for-byte before archiving.

The client used eight connections, 1024 cyclic keys, 64-byte values, 1000 warmup
commands/client, 20,000 requests at pipeline 1 and 1,000,000 at pipeline 16. Both
builds used the same toolchain and normal release profile; one owned server was
alive at a time. This is shared-runner evidence, not stable timing gates or a
controlled-hardware guarantee. Percentiles are **whole-batch** completions and
CPU counters are quantized observation windows, not exact request-only CPU time.

## Bottlenecks and changes

Profiling preceded the changes. Blocking PING/SET showed kernel receive
sleep/wake and scheduling-lock costs; PING excludes the key map. Fixed workers
also made extra receive attempts and deferred a newly read complete request until
the next pass. The original active-poll window could be rearmed indefinitely by
progress, so it did not bound continuous execution of oversubscribed lanes.

The changes keep safe Rust, zero Rust dependencies, randomized hashing, atomic
storage, worker counts, deadlines, admission, buffers and joined shutdown:

1. A guarded single-CPU/multiple-client hint yields after a single-command flush,
   not a batched flush. Default threading remains per-client.
2. Fixed lanes execute ready complete input in the receive pass while retaining
   one bounded read, 64 commands and bounded output/backpressure per pass.
3. Multiple lanes/clients have a separate 100 µs cooperative run-budget hint.
   Progress cannot rearm it; v2 restarts the interval when yielding/parking returns.
   Explicit wait is not charged to the next interval. The OS may ignore a yield;
   this is not epoll, a CPU quota or a hard fairness/latency guarantee.
4. Embedded JSON records the bind-time policy and version. The reader revalidated
   the actual v1 cohort under v2 without relabeling or rewriting its publication.

An unconditional reply-yield prototype was rejected after harming batched
throughput in an exploratory screen. V1 improved many worker tails but exposed
batched-throughput costs; review found that time spent yielded could immediately
consume the next run budget. V2 corrects that accounting. V1 and v2 ran on
**different runners/cohorts**: compare before/after inside each study, not their
absolute rates or the difference between their percentage gains.

## Final v2 findings

| Condition | Before → after cmd/s | Before → after batch p99 µs | Interpretation |
| --- | ---: | ---: | --- |
| Four workers, inherited CPUs, SET pipeline 1 | 137053 → 155761 (+13.7%) | 1053.0 → 272.7 | Higher rate, substantially lower tail |
| Four workers, inherited CPUs, SET pipeline 16 | 1737900 → 2024164 (+16.5%) | 1107.4 → 276.1 | CPU 1.22 → 1.04 µs/command |
| Four workers, one CPU, SET pipeline 1 | 88415 → 89266 (+1.0%) | 3222.1 → 383.6 | Roughly 88% lower batch p99, rate near baseline |
| Four workers, one CPU, SET pipeline 16 | 1168822 → 1175026 (+0.5%) | 3266.2 → 391.7 | Large tail reduction, rate near baseline |
| One worker, one CPU, SET pipeline 1 | 90231 → 95492 (+5.8%) | 118.0 → 107.2 | Same-pass I/O also helps without a multi-lane budget |
| Default per-client, one CPU, SET pipeline 1 | 76748 → 79243 (+3.3%) | 201.1 → 173.5 | Modest improvement; not a general victory |

All five four-worker/inherited pipeline-1 rates improved **12.8–15.9%**, with
batch p99 falling from roughly 1 ms to 0.27–0.36 ms. Four-worker/one-CPU store
pipeline-16 rates were near baseline (+0.5–2.8%) while batch p99 fell to roughly
0.39–0.42 ms from 3.26–3.62 ms. One-worker/one-CPU pipeline-1 rates improved
5.8–10.3% across workloads, with lower batch p99.

**Regressions are not omitted:** four-worker/one-CPU pipeline-16 PING throughput
fell **7.4%** (1470841 → 1361615), while p99 fell 3222.8 → 398.1 µs and sampled
CPU rose 0.68 → 0.74 µs/command. Default/inherited pipeline-1 XX fell **3.5%**;
default/inherited pipeline-16 GET fell **3.3%**. Default/one-CPU PING and GET
pipeline-1 tails worsened despite slightly higher rates. Other small rate/tail
regressions and overlap are visible in the full table; three runs do not establish
statistical certainty. No claim that every benchmark or metric got better is made.

For a one-CPU budget, `--threads 1` remains a useful starting point to evaluate:
in this cohort its SET pipeline-1 result was 95492 commands/s and 107.2 µs batch
p99, versus 89266/383.6 for four workers. Mode order was not fully counterbalanced;
this is not a universal tuning recommendation or a direct competitor comparison.

## Current Redis/Valkey comparison

The independent [reference report](../../reports/40230615995-1.md) validates
180 native records, 12 idle samples and 30 separately validated embedded records,
with genuine **gpt-6-luna** interpretation (workflow-token authentication,
automatic selection fallback disclosed). That assessment covers its own reference
cohort, **not either A/B study**.

Default equal-one-CPU SET remains **10.1% behind Redis at pipeline 1**: 52406
versus 58265 commands/s; batch p99 198.9 versus 189.7 µs. At pipeline 16 it leads
rate by 15.2%, but has worse batch p99 (378.0 versus 307.7 µs). Inherited-budget
Rillcache uses multiple CPUs. These results do not establish full Redis feature
compatibility or a general performance win, and cannot be compared as speedups
against a different runner's previous report.

## Validation and remaining work

124 tests per mode in debug/release; current Redis 8.10.2 and Valkey 9.1.2 common
wire corpus plus explicit divergence checks; 30 extra release TCP suites; exact
package/checksum tests; native amd64/arm64 image tests and credential-free pulls.
The downloaded release and exact public image were independently exercised in all
three modes, including health checks, conformance and reply-validated workloads.

Next investigations: native fixed-worker/reference comparisons with identical CPU
budgets, controlled longer repetitions, client/kernel saturation, mixed TTL/traffic
and value sizes. Preserve idle/backpressure/shutdown/atomicity guarantees. Native
readiness and secure-production capabilities still need explicit design decisions;
no unsafe shortcut or production-readiness claim follows from these measurements.
